# Q-T18 — Chat tags: decisions needed before a spec can be written

The code supports several incompatible designs and the task text does not pick one. Answers below make the file list and UI spec deterministic.

## Context (what the code already tells us)
- `ChatRecord` (`src/core/contracts/chat.ts:23-62`) and `ChatSummary`/`ChatListItem` (`:299-332`) have no tag fields. `listChats()` (`src/store/chats.ts:84-105`)` spreads the record into the summary, so new fields flow to `GET /api/chats` automatically.
- Chats are JSON files at `<data>/chats/<id>.json` (`config.ts:32`, `src/store/chats.ts:24-27`). `CURRENT_CHAT_VERSION = 2`.
- Tool calls are already persisted as native `AssistantMessage.content` `toolCall` blocks (`src/core/native-messages.ts:104-105`, `src/core/view.ts:246-260,342-351`); inputs are available as `block.arguments`. A free extractor needs no tool changes.
- Path helper: `resolveSourcePath` in `src/agent/tools/fs-shared.ts:179-188`. Study keys are validated `^[A-Za-z0-9_-]{1,80}$` (`src/store/study.ts:48`), so subject display names are not slugs.
- Session search is title-only fuzzy matching: `components/sidebar.tsx:413-430` calls `fuzzyScore(q, c.title)`; `fuzzyScore(query, ...fields)` already accepts multiple fields (`src/core/fuzzy.ts:8-18`) and requires every token to match some field.
- Store event law: `chats-changed` is emitted only for create/rename/delete (`src/store/chats.ts:29-37`); content writers are silent.
- Small-task route already exists (`src/core/settings-resolution.ts:125-163`); `submit_title`/`submit_topics` usage labels exist in `src/agent/subagents/submit-agent.ts:21-29`.

## Questions for the owner
1. **Tag data shape** — `tags: { topics: string[]; files: string[] }` on `ChatRecord`, or separate `topics`/`accessedFiles` fields? What metadata (e.g. `topicsGeneratedAt`) is stored, required or optional on old chats?
2. **What is a "topic"?** Free-text labels written by the model, or constrained to existing Study subject/topic names/IDs? What happens for unfiled chats, or when a Study topic is renamed/deleted?
3. **File provenance source of truth** — only `read` / `show_image` tool inputs, also `ls`/`find`/`grep` (patterns and result paths), user-attached message files, or Study material IDs? Are directories or glob patterns shown as file tags?
4. **File display form** — raw model input (`~/notes/lecture.md`), canonical absolute path, basename only, or Study material name? (Absolute home paths in a sidebar are a privacy/UX decision.)
5. **"Once per chat per day"** — rolling 24 h since last success, local calendar day, or UTC day? Where is the stamp stored? Does a failed call consume the day's one attempt?
6. **Filter UX** — extend the existing fuzzy search with tag fields, or add separate topic/file chips/dropdowns? Single- or multi-select? AND or OR between topic and file filters, and where does filter state live?
7. **Event semantics** — should a tag write emit `chats-changed` immediately (like `renameChat`) or stay silent like content writes and rely on turn events (`tests/chat-store-events.test.ts`)?
8. **Schema/init** — bump `CURRENT_CHAT_VERSION` for additive tag fields, or rely on optional absence? Should new chats be created with empty arrays/stamps?
9. **Ownership vs T19** — T19 also names "tags" as a helper job. Should T19 implement the cheap topic-tagging call (and T18 only add file tags + list UI/filter), or should T18 own the whole tag pipeline?

## Must NOT change regardless of answers
- No new API keys, no writes to `auth.json` outside `src/store/auth.ts`, no glass/scene UI — theme brief: opaque surfaces, existing `--lh-*` semantic tokens only.
