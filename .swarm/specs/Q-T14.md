# Q-T14 — OpenRouter fallback: decisions needed before a spec can be written

No code was read as authority for these choices; the repo has no fallback implementation and no `"via OpenRouter fallback"` string. Answering these lets me turn this into a mechanical spec.

## Context (what the code already tells us)
- Admission gate: `src/server/chat-handler.ts:320-347` refuses a `claude-code` chat with HTTP 503 when `providerKeyPresent("claude-code")` is false; that is `claudeCodeEnabled() && getClaudeBinary() !== null` (`src/server/claude-code-config.ts:6-13`).
- Engine build: `chat-handler.ts:369-375` catches catalog failure → 503 "The selected model is unavailable."
- Runtime: Claude launch errors are converted to a provider stream error (`src/agent/claude-code/stream.ts:699-716`, `:263-270`), NOT a throw from `agent.continue()`; `src/server/pi/ui-stream.ts:293-306` is the loop-level catch. Write-ahead persist, live-agent registration and settlement have already happened by then (`:625-667`, `:884-885`, `:1037-1044`).
- Key loader to reuse: `providerKeyPresent("openrouter")` / `keyValue("OPENROUTER_API_KEY")` from `src/server/keys.ts:188-210`. Do NOT read `auth.json` or use `openRouterApiKey()` (env-only, no production caller).
- Existing small-task route: `smallTaskOpenRouter(record, keyPresent)` and `resolveRoleSpecRouted` (`src/core/settings-resolution.ts:125-163`), configured at `settings.agent.smallTasks.openRouter`. It is documented as "small/background tasks", not conversation fallback.
- `TurnUsage.model` is frozen from the original engine at `chat-handler.ts:713,944-956`; no wire event or message field carries a fallback label today.

## Questions for the owner
1. **Which OpenRouter model runs the fallback?** The `agent.smallTasks.openRouter.model` pick, a new dedicated fallback setting/picker, or a fixed model id? If a new setting: what are its name, default, and UI placement?
2. **Which failures trigger it?** Only `claudeCodeAvailable() === false` at admission, or also engine-build failure, CLI launch/version failure, signed-out/rate-limit/refusal/result errors? Does a turn that already streamed some text count?
3. **Does fallback apply when Claude Code opt-in is off?** Or only when the owner opted in and it then failed? (Falling back when opt-in is off changes the meaning of that explicit switch.)
4. **What exactly is "before streaming"?** No `start` event, no `text_start`, no delivered text chunk? What happens if Claude emits partial text then errors — discard and restart on OpenRouter, or keep the partial reply?
5. **Where must "via OpenRouter fallback" appear?** Inline under the assistant reply, the stats-bar turn row, the activity dock, a transient banner, the usage log, or all of them? Should the string be exact and persisted across reload, or transient?
6. **How is the successful turn accounted?** Should `TurnUsage.model` become `openrouter:<id>` (used for cost/price lookup) and should the failed Claude attempt also appear in usage?
7. **Should the original Claude error stay visible when fallback succeeds?** Today `session-core.ts:651-658,376-392` derives an error banner from any `stopReason: "error"`, so a failed Claude stream left in the replay would show an error next to a successful fallback.
8. **Scope:** main chat turns only, or also side questions, background jobs/extraction, compaction, practice sessions and subagents?
9. **If OpenRouter is also unavailable** (no key, no model picked, bad catalog id): show the original Claude error, a new "fallback unavailable" refusal, or a combined message?
10. **Retry granularity:** once per turn, or once per model call within a tool-using turn?

## Must NOT change regardless of answers
- `src/store/auth.ts` stays the only direct reader of `auth.json`; no new secret in `settings.json`.
- No re-post of the same input through `handleChatInput()` — that would duplicate persisted user messages, live-agent registration, settlement and usage rows.
