# Q-T19 — Free helper agent: decisions needed before a spec can be written

Several product decisions (what "free" means, where notes live, when they update) are not derivable from the repo. Answering these makes the implementation mechanical.

## Context (what the code already tells us)
- **Titles already exist**: `src/server/chat-title.ts:25-45` fires `titleAfterFirstTurn()` from the post-turn hook in `src/server/chat-handler.ts:935-958`; the worker `titleChat` (`src/agent/subagents/study-workers.ts:238-247`) uses `runSubmitAgent` with role `extractor` and tool `submit_title`.
- **Routing already exists**: `resolveEngine("extractor")` → `resolveRoleSpecRouted` → `smallTaskOpenRouter(record, providerKeyPresent("openrouter"))` (`src/core/settings-resolution.ts:125-163`). `extractor` is a cheap role; `ROLE_TASK`/`LEAN_ROLES` in `chat-handler.ts:175-188` label it `"extraction"`.
- **Usage labels** come from `submitTaskLabel(toolName, role)` in `src/agent/subagents/submit-agent.ts:21-29` (`TOOL_TASK` map). The Settings → Token "By task" table renders new labels automatically (`components/settings/token-section.tsx:140-145`). `handleChatInput` is an *ambient* `"chat"` task; helpers relabel themselves.
- **No `running.md` exists**. Study storage is `<data>/study/{library.json,materials/,memory/,pages/,notes/<key>.json,cards/<key>.json}` (`src/store/study.ts:1-12`); notebook keys allow only `^[A-Za-z0-9_-]{1,80}$` (`:48`). Subjects have generated IDs `sub_...` and free-text names with spaces (`src/core/study/model.ts:162-172`).
- **There is already a "running context"** — `Subject.context` / `Topic.context` in `library.json`, maintained by `keepContextAfterTurn` (`src/server/study-agent.ts:125-137`, throttled 10 min / 8 turns). It is not a Markdown file.
- **Daily/idempotency precedent**: `graphUpdateDue()` and `LAST_UPDATE_FILE` in `src/server/graph-update-scheduler.ts:18-34`.

## Questions for the owner
1. **What does "free" mean?** Any configured OpenRouter small-task model (the existing setting), specifically an OpenRouter model with a `:free` suffix, or simply "cheap/background"? If no OpenRouter key or model is configured, should helpers skip entirely, fall back to the cheap slot, or use the strong slot?
2. **Role/model design** — reuse `extractor`, or add a dedicated `helper` `ModelRole` (which would change `config.ts`, `settings.ts`, `settings-resolution.ts`, `settings-body.ts`, `token-section.tsx`, `chat-handler.ts` and their tests)?
3. **Job granularity** — one generalized helper call that returns title + tags + notes update together, or separate small jobs with different cadences? (T18 specifies one topic call per chat per day; titles run after the first turn; notes may have another cadence.)
4. **Running-notes root** — exactly where is `notes/<subject>/running.md`? `<data>/study/notes/<subject>/running.md`, the data root `<data>/notes/...`, the learner's home `~/notes/...`, or a user-configured folder? (The existing `notes/` dir holds flat `<key>.json` notebooks.)
5. **`<subject>` directory name** — Study subject **ID** (`sub_...`), display name, or slugified name? Names may contain spaces and non-ASCII characters; IDs are stable but opaque.
6. **File format/update rule** — rewrite the whole file, append-only, or merge named sections? Which sections are required for "open questions/todos"? How are resolved todos removed, and who consumes the file afterwards (plain text, Study notes UI, another agent)?
7. **Trigger** — after every chat turn, only placed/Study chats, only the first turn, a daily job, or an explicit user action? If scheduled, should it run from `instrumentation.ts` like the graph updater?
8. **Usage labels** — exact `TOOL_TASK` strings for tags and running notes (existing style is lowercase hyphenated: `"title"`, `"topics"`, `"context"`)? Should these jobs be `background: true` and appear in the activity dock via `beginStudyWork`, or only in the usage ledger?
9. **Relationship to T18** — should T19 write the topic tags onto the chat record (T18's data), or only titles + running notes, leaving all tag work to T18?

## Must NOT change regardless of answers
- No direct reads of `auth.json`; use `providerKeyPresent("openrouter")` / the keys seam.
- No new secret in `settings.json`; no glass/scene UI; keep existing opaque theme surfaces and `--lh-*` tokens.
- Helpers must never block the user turn or throw into it (`titleAfterFirstTurn` is the precedent: fire-and-forget with `.catch`).
